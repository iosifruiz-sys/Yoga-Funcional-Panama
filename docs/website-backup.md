# Резервное копирование сайта

## Установка и первый запуск

Сначала утвердить и вручную слить PR с Backup Website в main. Автоматическое
слияние не включать. До проверенного первого бэкапа не продолжать изменения CMS.
Workflow запускается только вручную на main и не изменяет репозиторий.
Он резервирует main на момент mirror clone, а не SHA запуска workflow.

1. GitHub → Actions → Backup Website → Run workflow → main → Run workflow.
2. Дождаться успешного завершения. Summary содержит SHA, размеры и ссылку скачивания.
3. Внизу страницы запуска в Artifacts скачать website-backup-<run id>-<attempt>.
   Распаковать внешний ZIP GitHub на компьютер и сохранить дополнительную копию
   на независимом носителе до истечения срока хранения.
4. Сверить SHA256SUMS и выполнить восстановление ниже из скачанного bundle.
5. Создать аннотированный тег именно на SHA из METADATA.json:

```sh
git fetch origin main --tags
git tag -a backup-before-decap-restructure-2026-10-23 <main_sha> -m "Verified backup before Decap restructure"
git push origin refs/tags/backup-before-decap-restructure-2026-10-23
```

Не перезаписывать существующий тег. Для его защиты администратор должен создать
активный tag ruleset с точным именем тега и запретом обновления и удаления,
без ненужных bypass-разрешений. Проверить правила отдельно: наличие тега само
по себе не означает защиту. Workflow имеет только contents: read и не создаёт тег.

## Состав

- `website-<UTC>-<полный SHA>.bundle`: вся достижимая история всех refs,
  предоставленных GitHub mirror clone, включая доступные ветки и теги.
- `website-<UTC>-<полный SHA>-sources.zip`: все Git-файлы main, включая скрытые
  отслеживаемые файлы; export-ignore не исключает файлы.
- `FILES.json`: точный список исходников; `REFS.txt`: refs и их SHA.
- `METADATA.json`, `REPORT.md`: время, SHA, размеры в байтах и результаты проверки.
- `SHA256SUMS`: контрольные суммы всех перечисленных файлов.

Хранение равно разрешённому настройками репозитория сроку github.retention_days
(для публичного репозитория максимум 90 дней). Это временное хранилище:
удаление run/repository также может удалить артефакт. Скачанная независимая копия обязательна.

Локальные .env, неотслеживаемые файлы, токен workflow и Git config не архивируются.
Проверка имён потенциальных секретных файлов охватывает всю достижимую историю
и останавливает создание бэкапа. Она не доказывает отсутствие секретов внутри
обычных файлов. Полная история сохраняет всё ранее закоммиченное содержимое;
избирательное удаление секретов несовместимо с точной копией истории.
При обнаружении секрета остановиться, отозвать его и согласовать очистку истории.

Не входят: GitHub Secrets/Variables, rulesets, настройки репозитория/Pages/DNS,
issues, обсуждения PR, releases и их вложения, Actions artifacts, удалённые
недостижимые коммиты, внешние сервисы и данные. LFS хранится как Git pointers;
внешние LFS-объекты требуют отдельного бэкапа. При submodule скрипт останавливается.

## Проверка скачивания и восстановление

Нужны Git, Python 3.11+; команды ниже выполняются в каталоге распакованного артефакта.
Для SHA256 в Git Bash/Linux/macOS:

```sh
sha256sum -c SHA256SUMS
git init --bare verify.git
git -C verify.git bundle verify ../website-<UTC>-<SHA>.bundle
git clone --mirror website-<UTC>-<SHA>.bundle restored.git
git -C restored.git fsck --full --strict
git -C restored.git show-ref
git clone --branch main restored.git restored-site
git -C restored-site rev-parse HEAD
git -C restored-site status --porcelain
```

SHA должен точно совпасть с main_sha из METADATA.json, refs — с REFS.txt,
status должен быть пустым. Все операции выполняются в новом временном каталоге.
Не использовать git push --mirror в действующий репозиторий: это может удалить refs.
Восстановление на GitHub выполнять отдельно в новом пустом репозитории после проверки.
ZIP предназначен для удобства; для истории и Git-режимов файлов использовать bundle.

Каждый run автоматически проверяет bundle verify, fsck, CRC и содержимое ZIP,
восстановление mirror со сверкой всех refs и checkout main со сверкой SHA.
После первого запуска отдельно проверить фактическое скачивание и восстановление
скачанного файла. До этого систему нельзя считать полностью проверенной.
