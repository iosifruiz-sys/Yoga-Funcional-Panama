# Recursos: заключение о безопасном объединении CMS

Статус: **внедрение остановлено; этот Draft PR содержит только заключение**. Конфигурация CMS, код сайта и контент остаются прежними. Merge не выполнять до отдельного решения о реализации.

## Исходное состояние

Аудит проведён от актуального на начало задачи `main`, коммит `29827cbbe74e96f37aa98db8db90223f05fb19c8`.

В `public/admin/config.yml` существуют три folder-коллекции: `resources_es`, `resources_ru`, `resources_en`. Они используют JSON в `src/content/resources/es`, `/ru`, `/en`. Поля одинаковы, кроме скрытого языка и `relatedArticle`: ES/RU используют relation с `blog_es`/`blog_ru`, EN — необязательную строку будущего slug. Других production-использований этих трёх CMS-идентификаторов не найдено; существующий CMS-тест проверяет их явно.

В репозитории один ресурс: `src/content/resources/es/que-tan-movil-eres.json`. Его статусы: `draft: false`, `approved: true`, порядок 1. Он связан с опубликованной ES-статьёй `que-tan-movil-eres`. Реальных записей RU/EN нет. Проверены уникальность полного ID и slug, совпадение языка и папки, все заполненные пути к файлам и изображению, наличие опубликованной связанной статьи.

Astro читает `resources` через glob `**/*.json`; схема `src/lib/resourceSchema.ts` допускает языки es/ru/en и строковый relatedArticle. `src/lib/resources.ts` требует совпадения language и префикса ID, исключает draft/неapproved/неполные материалы и разрешает связи только с опубликованными статьями того же языка. EN-блог пока отсутствует. Каталог генерируется только для ES через `src/pages/recursos/[...index].astro`; превью реализовано существующим dialog, отдельного маршрута превью нет.

## Варианты

1. **Одна files-коллекция без перемещения.** Сохраняет существующие документы, но не обеспечивает свободное создание новых ресурсов. Не соответствует задаче.
2. **Одна обычная folder-коллекция с корнем resources и path по языку.** Позволяет оставить файлы в `es/ru/en`, сохраняет независимые записи и текущую схему. Наиболее узкий вариант для дальнейшей проверки. Но общий relation не переключает blog-коллекцию по language автоматически.
3. **Одна folder-коллекция с переносом в плоский каталог.** Потребует изменения текущей проверки префикса ID и внесёт ненужную миграцию. Не рекомендуется.
4. **Встроенный i18n multiple_folders.** Совместим с формой существующих путей, но вводит редакторский процесс переводов с базовым языком. Сам по себе не доказывает динамический выбор разных blog-коллекций для relation. Независимость публикации и поведение строкового language нужно отдельно проверить на реальном CMS.
5. **Nested collections.** Добавляют дерево и работу с путями, но не решают ограничение relation. Для языковых подпапок не нужны.

Основания: [folder/path](https://decapcms.org/docs/collection-folder/), [i18n](https://decapcms.org/docs/i18n/), [relation](https://decapcms.org/docs/widgets/relation/), [custom widgets](https://decapcms.org/docs/custom-widgets/).

## Причина остановки

Документированный relation задаёт одну целевую коллекцию строкой. Простая замена трёх коллекций одной не сохраняет автоматически ES → Blog ES и RU → Blog RU. Подмена relatedArticle произвольной строкой для ES/RU не является равнозначной заменой существующего редактора.

Локально проверен эксперимент: одна folder-коллекция без миграции, выбор языка при создании, блокировка смены языка существующей записи и небольшой admin-only wrapper штатного relation. Он сохранял прежний строковый relatedArticle, выбирал Blog ES/RU и оставлял существующий EN slug до появления Blog EN. Для регистрации требовалось менять порядок инициализации админки.

В настоящем Decap из подключённого сайтом CDN, но с изолированным backend `test-repo` и данными только в памяти браузера:

- общий список отображал ES/RU/EN;
- существующая ES-запись и синтетическая RU-запись открывались с прежним значением связи;
- редактирование заголовка без сохранения работало, смена языка существующей записи была заблокирована;
- форма создания ES позволяла выбрать связанную статью;
- повторные сценарии создания RU не завершали выбор статьи; отдельный диагностический запуск с инструментированием запроса проходил. Надёжность обычного сценария не подтверждена;
- полный сценарий создания/редактирования EN не завершён после обнаружения проблемы RU.

Это не доказывает дефект production Turbo: тестовый backend и синхронизация состояния требуют дополнительной проверки. Но этого достаточно, чтобы **не предлагать непроверенный wrapper к слиянию**. Успешная сборка Astro не подтверждает работоспособность CMS. Экспериментальные изменения конфигурации, запуска админки, виджетов и тестов убраны из diff до создания Draft PR. Тестовые записи не записывались в репозиторий; Save/Publish не нажимались.
